# Token & Quota Economy Guide

Руководство и жесткие автономные правила для агентов по экономии квот, токенов контекста и предотвращению холостых циклов tool call. Пользователь не должен контролировать эти процессы вручную — агент соблюдает их строго и автономно.

---

## 1. Пресечение инерции исследования (Anti-Over-Investigation / Action-First)
* **Проблема**: Агент тратит квоту на исследование окружения, запуск проверочных утилит или поиск исходников внешних валидаторов вместо выполнения прямых инструкций.
* **Автономное правило**:
  - Если в запросе пользователя передан аудит, отчет об ошибках (например, Яндекс Игры, консольные логи, чеклист модерации) или четкие критерии — **немедленно переходить к правкам по этим критериям**.
  - **Запрещено** искать исходные коды сторонних верификаторов, тестирующих скриптов или исследовать глубокое окружение, если требования к целевому коду/файлу уже сформулированы в отчете.
  - Исследования допустимы только в том случае, если задача принципиально невыполнима без выяснения отсутствующей сигнатуры или интерфейса, и строго ограничены минимальным точечным запросом.
  - **Предохранитель качества (Anti-Band-Aid / Проверка зависимостей)**:
    * Запрещено «глушить» баги поверхностными заплатками (например, бездумная вставка `if x != null: return` в месте падения, если причина в невалидных данных от источника).
    * Если фикс затрагивает изменение сигнатуры метода, контракта данных или публичного сигнала/события, агент **обязан** сделать один точечный вызов `grep_search` для поиска мест вызова (`callers`), чтобы предотвратить скрытые регрессии.

## 2. Пакетная генерация и Scratch Batching для MCP и скриптов (Batching vs Micro-Steps)
* **Проблема**: Создание сцен, 3D-моделей, серий костюмов, анимаций или массовое редактирование объектов через десятки и сотни мелких пошаговых вызовов tool'ов (например, 126 вызовов Blender MCP) мгновенно сжигает лимиты.
* **Автономное правило**:
  - **Строго запрещено** создавать или модифицировать сложные структуры по одному объекту/ноде через длинную цепочку микро-вызовов tool'а.
  - **Паттерн Scratch Batching**:
    1. Агент пишет полный комплексный скрипт автоматизации (Python для Blender, Luau для Roblox, GDScript для Godot или JS/TS) в файл `scratch/<script_name>.*` с помощью `write_to_file`.
    2. Скрипт выполняется **одним вызовом** через `execute_blender_code`, CLI-утилиту движка или консольный запуск.
    3. Скрипт обязан возвращать краткий статус завершения в stdout (успех / ошибка / количество созданных сущностей), не забивая контекст.
  - Экономия: сокращение со 100+ вызовов до 1–2 пакетных операций.

## 3. Точечная навигация и запрет пейджинга (Marker-Based Targeted Reading vs Paging)
* **Проблема**: Последовательное линейное чтение файлов блоками по 100–800 строк (`view_file` с шагом 1..150, 151..300 и т.д.) лавинообразно сжигает контекстное окно.
* **Автономное правило**:
  - **Строго запрещено** последовательно «листать» файлы повторными вызовами `view_file`.
  - **Обязательный двухшаговый алгоритм чтения**:
    1. **Маркировка через grep**: использовать `grep_search` с флагом `MatchPerLine: true` для точного нахождения целевой функции, метода, класса или переменной. Инструмент возвращает точный номер строки.
    2. **Точечный диапазон**: вызывать `view_file` **ровно один раз** с узким диапазоном: $\pm 30$ строк вокруг найденного маркера (`StartLine = line - 30`, `EndLine = line + 30`).
    3. При необходимости охватить структуру неизвестного файла — сгенерировать компактный outline (AST / список классов и функций с номерами строк) через быстрый scratch-скрипт, а не вычитывать сырой текст.
  - **Предохранитель качества (Формула «Шапка + Метод» против контекстной слепоты)**:
    * Если файл содержит $\le 150$ строк — безопаснее и надежнее прочитать его целиком за 1 вызов `view_file` (~800 токенов).
    * Для крупных файлов ($> 150$ строк): чтобы не допустить дублирования существующих полей или конфликтов состояний, агент читает **ровно два фрагмента**:
      1. **Срез А (Заголовок класса)**: строки `1..45` (импорты, наследование, сигналы, поля класса, `@export`, переменные состояния).
      2. **Срез Б (Целевой код)**: `(line - 25) .. (line + 35)` вокруг найденного метода.
    * Запрещено менять логику метода вслепую без знания полей и состояния класса.

## 4. Защита от бесконечных циклов проб и ошибок (Fail-Fast: Правило двух ошибок)
* **Проблема**: Попытки угадать аргументы CLI, пути к бинарникам (например, `godot.exe headless`), параметры компиляции или сетевые порты перебором по 10–15 раз подряд с зависанием сессии.
* **Автономное правило**:
  - **Лимит попыток (Fail-Fast = 2)**: если команда сборки, запуска, теста или обращения к MCP завершилась ошибкой или пустым выводом/зависанием **2 раза подряд** по схожей причине — агент **обязан немедленно прервать цикл подбора**.
  - **Действие при срабатывании**:
    1. Запрещено делать 3-ю слепую попытку подбора флагов.
    2. Провести локальный анализ причины (отсутствие бинарника в PATH, конфликт портов, нехватка прав, неверная рабочая директория).
    3. Немедленно запросить недостающие данные (путь к исполняемому файлу, переменные окружения) у пользователя или предложить четкий выбор действий, не сжигая квоту.
  - **Предохранитель качества (Разграничение ошибок окружения и отладки алгоритмов)**:
    * Лимит в 2 ошибки строго действует на: вызовы неизвестных бинарников, сетевые порты, угадывание путей в PATH и слепой перебор CLI-флагов.
    * Лимит **НЕ блокирует** вдумчивую разработку и отладку алгоритмов по тестам: если запускаются unit-тесты или тесты логики, и каждый прогон возвращает полезный новый стек-трейс или сужает область бага, агент вправе довести отладку до конца.

## 5. Полный запрет тяжелых субагентов по умолчанию (Browser Subagent Strict Ban)
* **Проблема**: Автономный запуск `browser_subagent` без прямого указания пользователя порождает тяжелые дампы DOM, видеозаписи, скриншоты и многократно перезагружает браузер.
* **Автономное правило**:
  - Вызов `browser_subagent` **СТРОГО ЗАПРЕЩЕН ПО УМОЛЧАНИЮ** для любых задач локальной веб-разработки, верстки и проверки приложений.
  - **Исключение**: только если в текущем запросе пользователя содержится **явный и прямой приказ** на запуск браузерного агента (например: *"запусти browser_subagent для тестирования"*, *"проверь через браузерный агент"*).
  - **Стандартный протокол для Web**:
    1. Собрать проект / запустить локальный dev-сервер в фоновом режиме.
    2. Провести программную валидацию (линтер, unit-тесты, проверка статус-кода через curl/скрипт при необходимости).
    3. Завершить шаг и предоставить пользователю URL (например, `http://localhost:3000`) с чек-листом для ручной проверки в уже открытой вкладке браузера.

## 6. Изоляция этапов и протокол передачи контекста (Feature Handover Protocol)
* **Проблема**: Длинные сессии (300+ шагов на весь проект) раздувают контекст до сотен тысяч токенов, где каждый новый вопрос передает гигантскую историю и сжигает квоту за 1–2 шага.
* **Автономное правило**:
  - Поскольку агент не может программно нажать кнопку «Новый чат» в интерфейсе IDE, агент берет на себя **проактивный контроль границ этапов**:
  - Как только логический этап фичи завершен (например: *"создан и настроен базовый контроллер персонажа"*):
    1. Агент фиксирует результат и создает/обновляет файл передачи контекста `scratch/context_handoff.md` (или `walkthrough.md`) с 4 обязательными пунктами:
       - **Что сделано** и текущий статус;
       - **Ключевые пути** к созданным/измененным файлам;
       - **Архитектурные инварианты и табу** (соглашения по архитектуре, шинам сигналов, типам данных, которые нельзя нарушать в следующей сессии);
       - **Следующая запланированная задача**.
    2. Агент выводит **Стоп-сигнал изолированного этапа**:
       > 💡 **Этап завершен. Рекомендуется открыть новую сессию (New Session per Feature)** для сброса контекста (с ~100k+ токенов до 3k). В новом чате просто напишите: `Продолжаем по context_handoff.md`.
    3. Агент не начинает следующую крупную фичу в том же раздутом диалоге без подтверждения пользователя.

## 7. Надежный запуск команд в Windows PowerShell (PowerShell Scratch Pattern)
* Сложные многострочные скрипты, конвейеры с экранированием (`"`, `'`, `$`) никогда не передаются сырыми строками в `CommandLine`.
* Всегда сохранять исполняемый код в `scratch/run_*.py` / `scratch/run_*.ps1` и вызывать одной простой командой.

## 8. Архитектурный манифест по требованию (On-Demand Project Map / Architecture Index)
* **Проблема**: В средних и крупных репозиториях (от 10–15 файлов) агент тратит десятки тысяч токенов на слепой перебор файлов, рекурсивные поиски и выстраивание ложных гипотез при каждом запросе или багфиксе.
* **Автономное правило**:
  - **Запрет слепого создания**: Строго запрещено создавать `PROJECT_INDEX.md` самовольно в микро-проектах (< 10 файлов) или без активационного сигнала.
  - **Сигналы запуска (Activation Signals)**:
    1. *Прямая команда пользователя*: `Создай карту проекта`, `Проиндексируй проект`, `/index`, `Составь архитектурный манифест`.
    2. *Инициатива в крупных проектах*: Если в проекте $\ge 15$ файлов логики и манифест отсутствует, агент не создает его молча, а в первом ответе кратко предлагает:
       > 💡 *Проект содержит > 15 модулей. Напишите `Проиндексируй проект`, чтобы создать компактный `PROJECT_INDEX.md` за 1 шаг без расхода токенов и ускорить навигацию.*
  - **Протокол сборки для существующих проектов (Zero-LLM Token Scanner)**:
    1. **Запрещено** читать тела файлов через `view_file` для составления карты — это сжигает квоту.
    2. Создать и запустить локальный скрипт `scratch/fast_indexer.py` (или `.ps1`) через `run_command`. Скрипт обходит директории, игнорирует служебный мусор (`.git`, `node_modules`, `.godot`, `build`, `dist`, `addons`, `.import`) и вытягивает только имена классов, `extends`, сигналы и ключевые функции.
    3. Вывод скрипта агент преобразует в компактный `PROJECT_INDEX.md` (строго $\le 150\text{--}200$ строк, $\approx 1.5\text{--}2\text{k}$ токенов) **ровно за 1 вызов**.
    4. **Автономное закрепление (Atomic 1-Step Setup)**: В этом же шаге агент обязан автоматически создать или дополнить `AGENTS.md` в корне проекта правилом `PROJECT_INDEX First`. Пользователю не нужно отдельно настраивать агента — проектная память фиксируется за 1 запрос.
  - **Правило синхронизации (Sync on Feature Handover)**:
    - При завершении крупного этапа разработки фичи (Раздел 6), если были добавлены новые подсистемы, менеджеры или контракты, агент одновременно с обновлением `context_handoff.md` актуализирует соответствующие строки в `PROJECT_INDEX.md`.

## 9. Протоколы гигиены контекста и надежности агентов (NVIDIA / Anthropic / Obra / Pocock)
* **Проблема**: Засорение контекста длинными листингами вспомогательных скриптов, простынями логов от субагентов, ложными фиксами без проверки и бесконечными переделками из-за непроясненных требований.
* **Автономные правила**:
  1. **Black-Box CLI Scripts (паттерн Anthropic)**:
     - Любые скрипты автоматизации и утилиты из директории `scratch/` запускаются строго через терминал (`run_command`).
     - **Запрещено** считывать их исходный код обратно в контекст через `view_file`.
     - Скрипты обязаны форматировать вывод компактно; агент читает только статус (код выхода, ошибки, агрегированный результат).
  2. **Жесткий контракт сдачи субагента без сырых логов (паттерн NVIDIA ModelOpt)**:
     - При вызове субагента (`invoke_subagent`), ему передается узкая изолированная задача.
     - Субагенту **категорически запрещено** возвращать в диалог сырые логи терминала, дампы сборки или объемные рассуждения.
     - Формат отчета субагента строго стандартизирован:
       * `Status`: `SUCCESS` или `BLOCKED`
       * `Target Files`: список созданных или измененных файлов
       * `Summary`: 1–2 предложения сути выполненных правок
       * `Verification`: результат проверки (код возврата `0`, пройденные тесты/сборка)
       * `Blockers`: описание причины остановки (только при статусе `BLOCKED`)
  3. **Архитектурный стоп-кран «Спроси до кода» (паттерн Matt Pocock)**:
     - При обнаружении явных противоречий в требованиях, неуказанном технологическом стеке или конфликте с архитектурными инвариантами агент **обязан остановиться до генерации кода**.
     - Запрещено писать 200–500 строк кода наугад в надежде угадать намерение пользователя.
     - Агент формулирует **1–2 четких вопроса** с готовыми вариантами выбора (через `ask_question` или обычный текст), экономя десятки тысяч токенов на переписывании кода.
  4. **Шлюз верификации до рапорта (Verification Before Completion Gate — паттерн Obra/Superpowers)**:
     - Агент не имеет права рапортовать пользователю о завершении задачи или закрытии бага, пока изменение не проверено объективной командой:
       * Запуск юнит-тестов / сьюта проверок (`run_command`);
       * Валидация синтаксиса или тестовая компиляция (например, headless-проверка движка или линтер);
       * Получение кода возврата `0`.
     - Запрещены фразы «я всё исправил, должно работать» без фактического запуска проверки там, где доступна среда исполнения.
